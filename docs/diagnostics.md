# Insight 1.2 诊断功能

在 Console → Insight →「诊断」中查看。兼容 Halo 2.26+、Java 21+。
1.2.0 沿用 SQLite v5；从早期 v4 升级时自动迁移至 v5。升级前建议在插件停止后备份整个 insight 数据目录，
回退旧版时同时恢复匹配的备份，避免让旧版读取新版数据库。

## 压力评分与单插件详情

「性能 → 持续高消耗插件 → 评分依据」展示维度分、加权贡献分和强度系数。
总分为最高维度分的 75% 加四维平均分的 25%；最高维同分时平分其贡献。
强度系数最高为 1，最终压力评分范围为 0–100，两者不是同一指标。
CPU、分配和请求耗时强度分别在单核 10%、64 MiB/min 和累计 15 秒/min 时取满。
线程维度使用驻留线程数与驻留分钟比例；4 个线程持续驻留且其他维度为零时仍约为 9.1 分。
页面同时显示 CPU 活动分钟与线程驻留分钟，帮助区分线程存在和线程忙碌。

点击性能页两个插件排行中的插件名称，打开单插件诊断。按需查询所选时间范围，
展示资源趋势、按 P95 排名的该插件接口、最近启停/版本/异常事件，以及最近 10 条优化报告。
资源趋势覆盖整个查询范围，汇总为最多 122 个点；接口最多 10 项，事件最多 20 条。
优化报告不受时间范围筛选。日志页默认选中该插件，仅有诊断权限时显示并请求日志接口。

「基线对比」可选择前一时段、昨天同一时段、上周同一时段或最近升级前后。
比较完整分钟，升级所在分钟排除；升级后的完整窗口尚未积累时明确提示等待。
昨天/上周对比的窗口不得重叠；超长范围需缩短。资源覆盖不足 75% 或不足 3 分钟、
请求量或采样密度差异超过 25% 会提示限制。CPU 与分配速率只按有计数的分钟平均，
计数缺失和无请求时相应数值显示不可用。升级时间来自 Insight 已记录的版本变更事件，
缺失记录时不会推测升级时间；历史保留不足时也不会补造基线。比较不证明变化由升级引起。

## 自身开销

「诊断 → 自身开销」显示采集/诊断任务平均和最大耗时、CPU 时间、分配量及 SQLite 读写次数，
保留最近一小时的分钟记录，插件重启后重新累计。面板首次打开时查询，随后手动刷新。
指标记录在既有操作的起止处，不增加采样线程、不另行写入数据库。
CPU 和分配量仅覆盖任务执行线程及其同步调用，其他请求线程和异步通知不包含在内。
SQLite 次数按操作统计，重试的一次操作计一次，失败单独计数，不等于 SQL 语句数。
详细口径与低开销策略见 [Insight 自身开销](monitoring-overhead.md)。

## 优化前后对比

从性能页的插件建议中选择停用，先保存最近 5 个完整分钟的基线，再调用 Halo 官方插件启停接口。
确认实际已停用后，从下一完整分钟起观察 5 分钟，等待 30 秒聚合落盘后生成报告。
对比进程 CPU、平均堆、GC 时间占比、请求 P95，同时展示请求量与采样覆盖。
无流量时 P95 显示不可用；采样不足或跨进程重启不能得出有效结论。

「诊断 → 优化效果」保存报告并提供重新启用入口。观察中提前启用插件会中断观察，
Insight 重启也会标记未完成观察中断。停用后确认接口失败会明确提示插件可能已经停用，
可到 Halo 插件页恢复。停用可能影响该插件的业务，因此需要用户确认且拥有 Halo 插件管理权限。
流量和其他操作会影响结果，对比不能证明所有变化都由该插件引起。

## 内存与 GC

- 最近 1/5/15 分钟 GC 时间占比按累计计数差值计算；覆盖不足、采样断档、数据过期或 JVM 重启显示采样不足。
- GC 后堆曲线来自真实 GC 完成通知，保留每分钟最低值。最近一小时至少 10 个点且跨越 15 分钟、
  最近 5 分钟有新点、净增长超过 32 MiB 且至少 70% 区间上升时提示持续增长。
- 年轻代回收后的堆量不等于全堆存活量；插件排行的分配字节也不等于插件当前持有内存，均不能单独证明泄漏。
- JFR 需手动启动，可录制 30/60/120 秒，一次只允许一个会话，提供 CPU/分配热点摘要和原始文件下载。
  仅启用指定诊断事件，不采集 JVM 系统属性和环境变量。使用 32 MiB 录制缓冲上限，文件保留最近 3 份、最多 3 天，
  插件运行时每分钟清理；插件停止期间不会执行清理。重启后未完成会话显示中断。

JFR 数据存在 SQLite 同目录下的 diagnostics 文件夹。普通监控 JSON 导出排除 JFR 堆栈和通知载荷；
JFR 下载需单独的诊断权限。录制上限是 JFR 的缓冲策略，实际文件大小可能因块边界略有偏差。

## 告警与通知

插件设置增加「高级诊断告警」与近期 GC 阈值，复用持续时间、冷却和恢复机制。
新增持续高消耗插件、依赖故障、近期 GC 压力、持续堆增长及任务异常规则。
业务任务异常当前包含最近一小时失败的备份、运行超过 30 分钟的备份、待执行队列至少 100 项。
指标未知时暂停判断，不能自动当作恢复。关闭规则也暂停判断、取消该活动告警待重试通知，
保留已有告警供确认；重新开启后按真实指标恢复评估。

新告警打开时保存首次触发现场，可在「告警 → 查看首次触发现场」展开。
包含当时系统采样、请求窗口、触发前 15 分钟已落盘的前 5 个插件与前 5 个接口证据，
可能有聚合延迟；缺失数据明确提示。告警后续更新、确认和恢复不会覆盖首次现场。
旧告警不补造现场。现场只保存有限的结构化数据，不包含原始日志、调用栈或请求正文。

各渠道先写 SQLite，再发送；失败按 30/60/120/240 秒退避，最多尝试 5 次，跨重启继续。
「通知投递」展示渠道、状态、尝试次数及下次时间。确认告警取消其尚未恢复的待重试通知，
新状态替代旧的待重试消息；已经在发送中的消息无法撤回。渠道禁用会记为跳过。
数据库不可用时尝试即时通知，并明确缺少持久化重试保障。成功仅表示渠道接受，不代表收件人阅读。
网络断开或进程崩溃发生在发送成功后、状态写入前时可能重复投递。

## 业务任务和故障定位

业务任务读取实际 Halo 备份记录（最近 200 条），包括状态、起止时间、耗时、失败原因，
并采集宿主公开的 ThreadPoolExecutor / Spring 线程池。区分未来计划任务和已到期等待任务，
队列扫描最多 1000 项。历史每分钟记录，页面展示最近 60 份快照。
未暴露指标的 Halo 内部队列和第三方插件任务无法通用归属，页面明确标注覆盖范围。

线程页手动读取热点线程和死锁线程，展示 CPU 增量、线程状态、锁拥有者及最多 32 层调用栈。
CPU 计数最多覆盖 512 个线程，默认展示前 30 个热点并补充死锁线程，合计最多 100 个。

日志页只读取 Halo 已配置的文件日志，无任意路径输入。可选择插件、来源、级别和关键词，
首次查询读取文件末尾最多 512 KiB，按从新到旧分页，每页 20/50/100 条，异常聚合覆盖当前筛选结果。
选择插件、来源、级别或每页数量后自动查询并回到第一页；关键词输入后点击查询。

翻页使用不可变查询快照，文件新增或轮转不会使原结果错页。「读取新增日志」只读上次位置之后的完整行，
多行异常续接上一条记录；未完成的行等待下次读取。文件轮转/截断/末尾重写会重新定位，
新增超过 512 KiB 则只保留末尾范围，并提示中间记录未读取。旧快照仍可翻页。
每个快照最多保留 512 Ki 个字符和 10,000 条已脱敏记录，进程内最多 16 个快照，
合计正文最多 4 Mi 个字符；不持有文件句柄。快照有效期 5 分钟，达到数量/容量限制也会提前回收，
过期时提示重新查询。页面不自动轮询日志，未提交的关键词不会影响翻页或增量读取。

插件归属通过插件包中的类名匹配 logger 与异常堆栈，不通过消息中提到的插件名称推断。
支持 Spring Boot 常见日志格式和包名缩写的 logger；缩写或共享类无法唯一识别时不自动归属。
同一异常栈涉及多个插件，会在这些插件的筛选结果中作为关联日志展示，不代表错误由其中某个插件引起。
自定义 logger、嵌套依赖库、未知日志格式和无法取得类索引的插件可能无法归属，相关记录保留在「全部日志」。
已卸载插件的历史记录也不保证能够归属。

类索引仅在查询日志时建立，最多每分钟刷新一次，不加载插件类、不增加后台采集线程；
单插件最多检查 20,000 个文件条目，合计最多索引 100,000 个类名。索引不完整时不自动匹配缩写 logger。
不提供整个历史日志库的全文检索。常见凭据会脱敏，业务信息仍可能出现在日志或调用栈中。

## 权限、保留与开销

查看监控权限可读指标、优化报告、业务任务、自身开销和单插件结构化诊断/基线；管理监控权限可操作优化记录、查看通知历史。
「访问日志、线程栈与 JFR 诊断」是额外权限，依赖管理监控权限，普通查看者不能调用这些接口。
停用/重新启用插件还需要 Halo 原生插件管理权限。所有诊断 API 均需登录授权。

诊断结构化历史遵循事件保留天数，并对每类记录设置最多 2000 条的硬上限，先达到者优先清理。
「清理全部」会删除诊断摘要和已结束的投递历史，保留仍待发送的通知；JFR 文件单独按上述限额清理。
每 15 秒检查近期 GC 信号，线程 CPU 采样跟随采集配置，低开销模式至少间隔 30 秒且最多检查 256 个线程。
每分钟保存堆趋势和任务快照；日志、线程栈、JFR 分析按需执行。
JFR 与诊断采样本身有开销，不将手动 GC 或自动停用其他插件作为后台默认行为。

## 站外存活监测

独立探针代码和 Docker 配置位于 external-monitor，部署步骤见 [站外监测部署](external-monitor.md)。
它不依赖 Halo 进程，通过站点响应判定宕机和恢复。需在另一台服务器配置目标和独立通知渠道后启动，
仅安装 Insight 插件不会自动获得站外宕机告警。
