# Insight 自身开销

性能页的 CPU 份额是插件归因 CPU 耗时占采样线程总 CPU 耗时的比例。
其他线程消耗很低时，Insight 的份额可能较高；这不等于 Insight 占用整机同样比例的 CPU。
内存分配速率也不等于当前驻留内存。评估监控负担应结合 Halo 进程 CPU、GC 时间占比、
线程诊断里的单核 CPU 使用率，以及同等请求量下的前后对比。

## 已减少的持续工作

- 优化观察只在启动时恢复进行中的任务。空闲 tick 不再读取并解析最近 100 条观察历史；
  新任务先落盘再更新内存状态，完成写入失败时保留任务并在下一轮重试。
  历史页面仍按需查询 SQLite，插件重新启动时仍将未完成任务标记为中断。
- 支持扩展 ThreadMXBean 的 JVM 使用一次批量调用读取线程 CPU 计数，
  替代每轮最多 512 次逐线程调用；不支持扩展接口时保留逐线程读取。
- 线程诊断跟随运行时采样策略：标准配置下约 15 秒、最多 512 个线程；
  低开销模式下至少 30 秒、最多 256 个线程。恢复标准采集后重新使用配置值。
  周期检查仍为 15 秒，因此实际诊断采样间隔向检查周期对齐。
- 仪表盘保持运行概要刷新，只为当前可见页面加载历史数据。
  优化排行仅在优化弹窗打开时查询。默认概要页每轮由 4 个请求减少到 2 个请求；
  诊断页的全局刷新由 4 个请求减少到 1 个请求，诊断面板自身的数据仍按原周期刷新。

压力评分公式与排行规则保持原有计算。常驻线程仍可能贡献约 9 分，
不能要求优化后的评分必然下降，也不能单凭 CPU 份额承诺减少了多少实际 CPU 使用量。

## 1.2.0 的自身开销测量

在「诊断 → 自身开销」查看最近一小时的采集/诊断任务耗时、单核 CPU 估算、
分配速率、SQLite 读取和写入次数。展开每分钟记录可观察工作量变化。
计数不可用时显示不可用，不把未知数值当成零；失败次数包含最终失败，SQLite 重试只计一次操作。

记录使用已有任务的起止点和 JVM 当前线程计数，每分钟保留内存聚合，最多 60 个点。
不额外启动线程、不写入测量历史；面板也不轮询。CPU 和分配量包含采集/诊断任务线程的
同步调用，不覆盖 API 请求线程和异步通知，因此不代表插件全部开销。
SQLite 操作计数覆盖经过连接管理器的读写，不等于 SQL 语句数。插件停止再启动会重置窗口。

新单插件详情与基线对比均手动读取，日志翻页复用查询快照，新增读取验证游标后只取新增完整行。
首次告警现场只在新告警打开时捕获，同一轮评估共用一份；不会每轮反复查询排行并覆盖首次证据。

## 使用与验证

在性能诊断弹窗的「Insight 自身开销」中点击「降低监控器开销」，
将系统与 JVM 采样间隔设为至少 30 秒、资源归因扫描上限设为至多 256 个线程。
线程扫描覆盖减少时，部分线程消耗可能无法纳入归因；可恢复标准采集用于细查。

更新后分别在相同流量和页面状态下观察 15 分钟，比较 Halo 进程 CPU、GC 时间占比、
Insight 线程的 CPU 时间与分配速率。需要更细的热点定位时，可手动录制 60 秒 JFR。
较长时间范围的排行混合更新前后数据，宜选更新后的观测区间。

自动回归覆盖空闲读取次数、新任务完成、落盘失败重试、重启中断、
批量计数与 CPU 差值、低开销模式切换，以及页面和弹窗切换时的请求范围。
